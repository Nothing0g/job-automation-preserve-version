# Original Google Apps Script: Verification Notes

The script’s primary operational failure is a repeated misuse of `PropertiesService.getScriptProperties().getProperty(...)`. This method expects the **name** of a Script Property, but several calls pass an apparent property value instead. As a result, `callGemini` at line 57 looks up the literal API-key-like string rather than `GEMINI_API_KEY`, and therefore throws the intended “Missing GEMINI_API_KEY” error unless a property was accidentally created with that literal string as its name. The same issue occurs in `getBaseResumeText` at line 83, which looks up a literal document identifier rather than `RESUME_DOC_ID`.

The candidate and sending configuration contains the same defect. At line 133, the candidate name lookup should use `CANDIDATE_NAME`, but instead uses the candidate’s apparent name as the key. At line 224, the reply-to lookup should use `REPLY_TO_EMAIL`, but instead uses an apparent email address as the key. Those errors produce fallback or blank values, which weakens generated content and can prevent a valid reply-to configuration from being used.

The script also defines `dailyAutomation` but does not create or document installation of a time-driven trigger. Its scheduled scraping/generation routine therefore will not run on its own until a trigger is manually configured in Google Apps Script. The original workflow additionally includes third-party scraping and Gmail sending; those functions are intentionally not reproduced because the requested website is limited to job intake, tracked statuses, grounded drafts, editable workspaces, and copy/download exports.

The replacement does not copy secrets from the script. It eliminates the need to store a Google AI key or Gmail credentials in a spreadsheet script, and it keeps master-resume files separately from the application database. For AI generation, it enforces a source-of-truth rule: only the stored master resume, stored bio, and the job description may substantiate candidate claims.
